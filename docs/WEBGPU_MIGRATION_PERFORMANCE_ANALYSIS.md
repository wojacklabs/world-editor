## 1. 현재 렌더링 파이프라인 병목점 분석

### 1-1. 드로우콜 병목 (CPU-Bound)

현재 프레임당 드로우콜 수를 코드에서 계산하면:

**식생 시스템 (FoliageSystem):**
```
지형 크기: terrainScale (기본 512)
청크 크기: 16×16
→ 청크 수: (512/16)² = 32×32 = 1,024개 청크

청크당 InstancedMesh (최대):
  - grass_v0, grass_v1, grass_v2, grass_v3  = 4개
  - rock_v0, rock_v1, rock_v2, rock_v3      = 4개
  - pebble                                   = 1개
  - sandRock                                 = 1개
→ 청크당 최대 10개 드로우콜

인스턴스 밀도:
  grass:    baseDensity 8.0  × 256㎡/청크 = 2,048 인스턴스/청크
  pebble:   baseDensity 0.5  × 256㎡ = 128 인스턴스/청크
  rock:     baseDensity 0.15 × 256㎡ = 38 인스턴스/청크
  sandRock: baseDensity 0.05 × 256㎡ = 12 인스턴스/청크

식생 총 드로우콜: 1,024 × 10 = 최대 ~10,240 드로우콜
(LOD 컬링으로 실제 ~2,000-4,000, 여전히 매우 많음)
```

**기타 드로우콜:**
```
지형 메시:            1-2 (LOD 레벨)
물 메시 + 반사 패스:  2 + 반사 씬 렌더링 (전체 다시 그림)
하늘/구름:            2-3
날씨 파티클:          1-2 (비 5,000 / 눈 3,500 빌보드)
프롭 (배치 오브젝트):  50-300개 (LOD 3단계)
그림자 패스:          위 전체 한 번 더 (섀도맵 렌더링)
포스트 프로세싱:      3-4 (안개 + 블룸 다운샘플 + 톤매핑)
임포스터 아틀라스:    32 (8앵글 × 4타입, 온디맨드)
────────────────────────────────
총 추정: 3,000 ~ 5,000+ 드로우콜/프레임
```

**WebGL2의 문제:** 모든 드로우콜이 **싱글 스레드**에서 순차 실행. 각 드로우콜마다 상태 검증(State Validation)이 발생하여 CPU 오버헤드가 큼.

### 1-2. 식생 생성 CPU 병목

```typescript
// FoliageSystem.ts:1631 — CPU에서 인스턴스 하나하나 반복문으로 생성
for (let i = 0; i < instanceCount; i++) {
  const x = startX + this.seededRandom() * (endX - startX);
  const z = startZ + this.seededRandom() * (endZ - startZ);
  // 스플랫맵 읽기 + 높이 보간 + 경사 계산 + 매트릭스 생성 = 인스턴스당 ~5회 연산
}
// maxInstancesPerChunk = 5,000
// 1,024개 청크 × 최대 5,000 = 최대 5,120,000번 반복 (CPU)
// 인스턴스당 5회 연산 = 총 ~25,600,000 CPU 연산
```

### 1-3. 지형 셰이더 텍스처 샘플 병목

TerrainShader.ts 프래그먼트 셰이더의 텍스처 샘플 횟수:

```
픽셀당 텍스처 샘플:
  스플랫맵:                1회
  흙 (diffuse+normal+disp): 3회
  모래 패턴:               2회
  바위 hex-tiled:          ×3 (diffuse+ARM+normal+disp) × 2(hex blend) = 24회
  바위 triplanar:          ×3축 × 4맵(diffuse+ARM+normal+disp) = 12회
  풀 hex-tiled:            ×3 (diffuse+ARM+normal+disp) × 2(hex blend) = 24회
  매크로 변화:             2회
  섀도맵:                  1회
  ─────────────────────────
  총: 최대 ~46회 텍스처 샘플/픽셀 (!)
```

이것은 프래그먼트 셰이더에서 매우 무거운 수준이며, 특히 오버드로우가 있을 때 심각한 GPU 병목.
추가로 FBM 노이즈가 6 옥타브까지 실행(옥타브당 3회 텍스처 룩업 = 18회)되고,
Voronoi 연산(9 이웃 × 3회 = 27회)까지 합치면 **실질 ~70+ 연산/픽셀**.

### 1-4. 렌더 패스 구조

```
프레임당 렌더 패스:
  1. 섀도맵 패스 (전체 씬 렌더링)
  2. 물 반사 패스 (WebGLRenderTarget, 별도 씬 렌더링)
  3. 메인 패스 (전체 씬)
  4. 체적 안개 패스 (하프 해상도 레이마칭 16스텝 + 컴포짓)
  5. 포스트 프로세싱 (블룸 + 톤매핑)
  ─────────────────────
  총: 5~6 패스/프레임
```

**WebGL2의 문제:** 각 패스 전환 시 렌더 타겟 바인딩, 스테이트 리셋 등의 CPU 오버헤드 발생.

### 1-6. 유니폼 업데이트 병목

```
프레임당 유니폼 바인딩:
  지형 셰이더: ~30 유니폼 (포인트라이트 8개 × 3속성 포함)
  풀 셰이더:   ~15 유니폼 (바람, 색상, LOD)
  바위 셰이더: ~10 유니폼
  물 셰이더:   ~20 유니폼 (Gerstner 4파 × vec4 + 반사)
  날씨/하늘:   ~10 유니폼
  안개 패스:   ~10 유니폼
  ─────────────────────
  총: ~100+ 유니폼 업데이트/프레임
  + 머티리얼 전환: ~15-20회/프레임
```

### 1-7. 메모리 대역폭

```
프레임당 렌더 타겟 대역폭 (1920×1080):
  메인 패스:           1920×1080 × 4ch × 4B = 33.2 MB
  체적 안개 (하프):     960×540 × 4ch × 4B = 8.3 MB
  블룸 다운샘플 체인:   ~16 MB
  물 반사 타겟:         256×256 × 4ch × 1B = 0.3 MB
  섀도맵:              2048×2048 × 1ch × 4B = 16.8 MB
  출력:                33.2 MB
  ─────────────────────
  총: ~108 MB/프레임 × 60 FPS = ~6.5 GB/s 대역폭
```

## 2. WebGPU 전환 시 성능 개선 항목

### 2-1. 드로우콜 오버헤드 — 2~5배 개선

| 항목 | WebGL2 | WebGPU | 개선폭 |
|------|--------|--------|--------|
| **드로우콜 모델** | 순차 실행, 매번 상태 검증 | 커맨드 버퍼 사전 인코딩, PSO 캐싱 | **2~5×** |
| **파이프라인 전환** | 매 드로우콜마다 셰이더+상태 검증 | Pipeline State Object 한 번 생성, 재사용 | **3~10×** |
| **CPU 스레딩** | 싱글 스레드 | 커맨드 인코딩 멀티스레드 가능 | **2~4×** |

**현재 프로젝트 적용 시:**
```
현재:  ~3,000-5,000 드로우콜/프레임 → CPU 프레임타임 ~10-16ms
WebGPU: ~3,000-5,000 드로우콜/프레임 → CPU 프레임타임 ~3-5ms
→ CPU 프레임타임 약 3~4배 개선

+ Indirect Draw 적용 시:
  4,096 식생 드로우콜 → 4개 indirect draw (타입당 1개)
  → 드로우콜 ~99% 감소
```

### 2-2. GPU 간접 드로우 (Indirect Draw) — 식생 혁신

WebGPU의 `drawIndexedIndirect`로 **GPU가 직접 드로우 파라미터를 결정**:

```
현재 (WebGL2):
  CPU: 256개 청크 프러스텀 컬링 → visible 청크만 draw call
  CPU → GPU 전송: 매 프레임 가시성 데이터

WebGPU Indirect Draw:
  GPU Compute: 모든 청크 한 번에 프러스텀 컬링
  GPU: 비가시 청크의 instanceCount = 0 설정
  GPU: Indirect Draw로 한 번에 렌더링
  CPU 개입: 없음 (!)
```

**결과:** 식생 프러스텀 컬링이 CPU에서 GPU로 완전히 이동. CPU는 커맨드 버퍼 제출만 하면 됨.

### 2-3. Compute Shader — 식생 생성 150배 개선

현재 CPU에서 하는 무거운 작업을 GPU로 이전:

| 작업 | 현재 (CPU) | WebGPU Compute | 개선폭 |
|------|-----------|----------------|--------|
| **식생 인스턴스 생성** | JS 반복문 128만회 | GPU 병렬 워크그룹 | **50~150×** |
| **바람 텍스처 생성** | 256×256 FBM CPU 계산 | Compute Shader | **10~30×** |
| **하이트맵 편집** | JS Float32Array 조작 | Storage Buffer + Compute | **20~50×** |
| **스플랫맵 업데이트** | CPU 픽셀 단위 페인팅 | Compute Shader | **20~50×** |
| **프러스텀 컬링** | CPU 256 청크 순회 | Compute Shader | **10~20×** |
| **NavMesh 빌드** | Recast (CPU) | 일부 GPU 가속 가능 | **2~5×** |

**구체적 예시 — 식생 생성:**
```
현재:
  5,120,000 인스턴스 × (스플랫맵 읽기 + 높이 보간 + 경사 계산 + 매트릭스 생성)
  = CPU에서 ~200-500ms (지형 편집 후 generateAll() 호출 시 체감 랙)

WebGPU Compute:
  Dispatch(5120000 / 256 = 20,000 워크그룹, 각 256 스레드)
  = GPU에서 ~2-5ms
  → 약 100배 개선
```

### 2-4. 날씨 파티클 시스템 — 10~100배 스케일 업

```
현재:
  비/눈 파티클: CPU에서 위치 업데이트 → GPU 업로드
  → 최대 ~50,000 파티클 (CPU 한계)

WebGPU Compute:
  파티클 위치가 GPU Storage Buffer에 상주
  Compute Shader로 매 프레임 물리 업데이트
  → 1,000,000+ 파티클 가능 (GPU 내부에서 순환)
  → CPU→GPU 전송 = 0
```

### 2-5. 체적 안개 — 2~3배 개선

```
현재 (Fragment Shader 레이마칭):
  16 스텝 × 하프 해상도 = ~30만 픽셀 × 16 = 480만 샘플
  Fragment Shader는 Quad 단위 실행 → 비효율적 divergence

WebGPU Compute:
  Compute Shader로 3D 볼륨 텍스처 사전 생성
  → Froxel (Frustum Voxel) 기반 안개
  → 해상도 독립적, 시간 분할(Temporal) 가능
  → 동일 품질에서 2~3배 빠름
```

## 3. WebGPU 전환 시 품질 개선 항목

### 3-1. 실시간 GI (Global Illumination)

```
현재: 불가능 (WebGL2에 Compute 없음)
WebGPU: Compute Shader로 라이트 프로브/Voxel GI 가능

구체적 구현:
  - Voxel Cone Tracing (VXGI)
  - Screen-Space GI (SSGI) → Compute로 효율적 구현
  - Irradiance Probes → GPU에서 실시간 업데이트

효과: 나무 아래 그림자에 주변광 반사,
      동굴 입구의 간접광 등 사실적 조명
```

### 3-2. 나뭇잎/식생 개별 애니메이션

```
현재: 나무 전체가 sin() 하나로 흔들림
WebGPU: Compute Shader로 개별 잎/가지 물리 시뮬레이션

구체적 구현:
  Storage Buffer에 잎 상태 (위치, 속도, 가속도) 저장
  매 프레임 Compute로 스프링-댐퍼 물리 계산
  → 수십만 개의 잎이 각각 독립적으로 움직임
  → 바람 방향 변화에 물리적으로 반응
```

### 3-3. 물 시뮬레이션 고도화

```
현재: sin() 기반 파동 (시각적 근사)
WebGPU: FFT 기반 해양 시뮬레이션 (물리 기반)

구체적 구현:
  - Jerry Tessendorf Ocean (FFT)
  - Compute Shader로 256×256 FFT → 실시간 파고 맵
  - 거품, 물보라 파티클도 Compute로 처리

lib/loader/index.ts에 이미 주석 존재:
  "Interactive Water (WebGPU Compute Shader)
   - temporarily excluded pending Three.js WebGPU compute support"
→ 이미 계획되어 있었으나 WebGL2 한계로 보류된 기능
```

### 3-4. 고급 포스트 프로세싱

| 효과 | WebGL2 | WebGPU | 비고 |
|------|--------|--------|------|
| **SSAO** | Fragment 기반 (느림) | Compute 기반 (2~3배 빠름) | 더 많은 샘플 가능 |
| **SSR** | 불가/느림 | Compute Hi-Z Trace | 반사 품질 대폭 향상 |
| **모션 블러** | 기본적 | Compute Tile-based | 더 정확한 per-object 블러 |
| **DOF** | 가우시안 근사 | Compute 원형 보케 | 시네마틱 품질 |
| **TAA** | 가능하나 느림 | Compute + History Buffer | 안정적 안티에일리어싱 |

### 3-5. 텍스처 품질 개선

```
현재: 텍스처 배열 미지원 → 개별 uniform sampler2D
WebGPU: Bindless Textures / 텍스처 배열 네이티브 지원

효과:
  - 지형 셰이더의 46회 텍스처 샘플 → 텍스처 배열 + 인덱싱
  - 머티리얼 수 제한 없이 확장 가능
  - 바인딩 그룹 캐싱으로 상태 전환 최소화
```

### 3-6. 그림자 품질

```
현재: PCFSoftShadowMap (고정 해상도)
WebGPU: Virtual Shadow Maps (VSM) 구현 가능

구체적 구현:
  - Compute Shader로 타일 기반 섀도맵 할당
  - 가까운 물체는 고해상도, 먼 물체는 저해상도
  - 캐시 기반 → 정적 물체 섀도맵 재사용
  → 더 넓은 영역, 더 선명한 그림자
```

│                                                              │

                            ↓

│                                                              │
│ 결과: 60+ FPS 유지, 개별 잎 물리 애니메이션                     │
└─────────────────────────────────────────────────────────────┘
```

### 4-2. 지형 셰이더

```
┌─────────────────────────────────────────────────────────────┐
│                     현재 (WebGL2)                            │
├─────────────────────────────────────────────────────────────┤

## 5. 전환해도 개선 안 되는 것

WebGPU가 만능은 아닙니다. 다음은 **WebGPU로 바꿔도 달라지지 않는** 것들:

| 항목 | 이유 |
|------|------|
| **텍스처 업로드 속도** | GPU 메모리 대역폭 자체는 동일 |
| **셰이더 첫 컴파일 시간** | WGSL도 컴파일 필요 (오히려 초기 로딩이 약간 느려질 수 있음) |
| **지오메트리 폴리곤 수** | 같은 GPU에서 처리하는 폴리곤 수 한계는 동일 |
| **메모리 사용량** | 동일한 에셋은 동일한 VRAM 사용 |
| **네트워크/로딩** | 에셋 다운로드 속도는 API와 무관 |
| **IndexedDB 성능** | 저장/불러오기 속도는 브라우저 스토리지 제한 |
| **UI 렌더링 속도** | React/DOM 렌더링은 WebGPU와 무관 |

### 주의: 잠재적 단점

| 항목 | 설명 |
|------|------|
| **초기 로딩** | WebGPU 어댑터 요청 + 디바이스 초기화 (비동기) 추가 |
| **셰이더 컴파일** | WGSL 파이프라인 첫 생성 시 WebGL보다 약간 느릴 수 있음 |
| **디버깅 도구** | WebGL Inspector보다 WebGPU 디버깅 도구가 아직 미성숙 |
| **폴백 복잡성** | WebGPU 미지원 브라우저용 WebGL2 폴백 관리 필요 |

## 6. 종합 결론

### 수치 요약

| 지표 | 현재 (WebGL2) | WebGPU 전환 후 | 개선폭 |
|------|-------------|----------------|--------|
| **드로우콜 CPU 비용** | ~10-16ms/프레임 (5,000 DC) | ~3-5ms (Indirect 4 DC) | **3~4×** |
| **식생 생성 시간** | ~200-500ms (CPU 512만 인스턴스) | ~2-5ms (GPU Compute) | **~100×** |
| **프러스텀 컬링** | CPU 1,024 청크 순회 | GPU Compute | **10~20×** |
| **파티클 한계** | ~50,000 | ~1,000,000+ | **20×** |
| **바람 애니메이션** | 1단계 (전체 흔들림) | 5단계 (개별 잎 물리) | **품질 5×** |
| **체적 안개** | 16스텝 레이마칭 | Froxel + 시간분할 | **2~3× 빠름** |
| **물 시뮬레이션** | sin() 근사 | FFT 물리 기반 | **품질 대폭 향상** |
| **포스트 프로세싱** | Fragment 기반 | Compute 기반 | **2~3× 빠름** |
| **그림자 품질** | 고정 해상도 | Virtual Shadow Maps | **품질 향상** |
| **전체 FPS (예상)** | 30-45 FPS | 60+ FPS | **1.5~2×** |

### 핵심 포인트

> **가장 큰 개선은 Compute Shader입니다.**
>
> 현재 CPU에서 하는 무거운 작업 (식생 생성 128만 인스턴스, 프러스텀 컬링, 바람 텍스처 생성, 파티클 물리)이 전부 GPU로 이동하면서 CPU 병목이 해소됩니다.
>
> 드로우콜 오버헤드 감소도 중요하지만, 이 프로젝트에서는 **식생 시스템의 GPU 컴퓨트화**가 가장 체감이 클 것입니다. 지형 편집 시 식생 재생성이 300ms → 3ms로 줄면 실시간 편집 경험이 근본적으로 달라집니다.
>
> 품질 측면에서는 **개별 나뭇잎 물리 애니메이션**, **FFT 해양 시뮬레이션**, **체적 구름**, **GI** 등 WebGL2에서는 불가능했던 기능들이 열립니다.

### 전환 권장 여부

**강력히 권장합니다.**

이유:
1. 코드에 이미 WebGPU 호환성 주석이 곳곳에 있어 전환 의도가 확인됨
2. Interactive Water가 WebGPU Compute 대기 상태로 보류 중
3. Three.js r183+에서 WebGPURenderer가 프로덕션 레디
4. 2026년 기준 브라우저 지원율 ~95%+ (Safari 26 포함)
5. `import * as THREE from 'three/webgpu'`로 제로 컨피그 시작 가능
6. WebGL2 자동 폴백 내장

단, **커스텀 GLSL 셰이더 10개+의 TSL 전환 작업**이 가장 큰 마이그레이션 비용이며, 이를 점진적으로 진행하는 것이 현실적입니다.
